# Постановка: шлюз LiteLLM + OpenRouter + Telegram-бот с ролями

Документ — задание для Codex CLI (или другого агента), который будет разворачивать схему
с нуля на домашнем сервере. Проверено на живой установке в октябре 2026; грабли в конце
собраны оттуда же, а не из документации.

Все адреса, имена и бюджеты в тексте — заглушки вида `<...>`. Подставить до начала работ.

## Что должно получиться

Один HTTP-эндпоинт, за которым прячутся все LLM-провайдеры, и Telegram-бот, который
общается с человеком от лица нескольких ролей. Критерии приёмки:

1. `GET /health/liveliness` шлюза отвечает 200, `GET /v1/models` перечисляет настроенные
   маршруты.
2. Любой бот зовёт модель по короткому имени (`fast`, `smart`, `local`), не зная ни
   провайдера, ни его ключа, ни базового URL.
3. Расход по каждому боту и каждой модели виден в таблице `LiteLLM_SpendLogs` и
   ограничен бюджетом ключа.
4. В Telegram работает `/role` — переключение роли; у каждой роли свой системный промпт
   и свой набор моделей.
5. Приватные данные не уходят к зарубежным провайдерам: роль, работающая с ними,
   технически не может позвать облачную модель — её ключ таких маршрутов не знает.
6. Повторный запуск любого скрипта развёртывания ничего не ломает (идемпотентность),
   деструктивные операции по умолчанию в режиме dry-run.

## Что нужно получить от владельца до старта

| Что | Зачем | Формат |
|---|---|---|
| Хост под шлюз | Docker + 2 ГБ RAM хватит | ssh-доступ, sudo |
| Ключ OpenRouter | доступ к сотням моделей одним ключом | `sk-or-...`, с лимитом расхода на самом ключе |
| Ключ локального/регионального провайдера | контур для приватных данных | по провайдеру |
| Токен Telegram-бота | от `@BotFather` | `123456:ABC...` |
| Telegram user id владельца | белый список: бот отвечает только своим | число |
| Хост-посредник за пределами региона | если OpenRouter блокирует IP хоста | ssh-доступ |

## Шаг 1. Шлюз

LiteLLM в варианте с БД (`litellm-database`), рядом Postgres. Compose, два сервиса,
данные Postgres в именованном томе.

Требования:

- **Версия образа пинится явно.** Релизы выходят почти ежедневно, `latest` однажды
  приедет с изменённым поведением роутера.
- Шлюз **не публикуется в интернет**: слушает только адрес LAN или loopback. Снаружи —
  только через VPN владельца.
- Мастер-ключ (`LITELLM_MASTER_KEY`) и ключи провайдеров — в env-файле с `chmod 600`
  вне git. В репозитории только `*.env.example`.
- `store_model_in_db: true` и `database_url` — иначе не будет учёта расхода, а это
  главная причина, по которой шлюз вообще нужен.
- `pg_dump` по расписанию в локальный каталог, ротация на N копий, скрипт с `DRY_RUN=1`
  по умолчанию.

Проверка шага: `curl` по `/health/liveliness` → 200; `/v1/models` с мастер-ключом
перечисляет маршруты; в логах контейнера нет повторяющихся ошибок подключения к БД.

## Шаг 2. Выход к зарубежным провайдерам

OpenRouter отдаёт `403 Access denied by security policy` с адресов некоторых регионов и
части серверных подсетей. Если хост попадает под это, нужен посредник:

- На зарубежном хосте — HTTP-прокси (tinyproxy или аналог), слушающий **только
  loopback**.
- С хоста шлюза — ssh-туннель к этому порту под systemd-юнитом с автоперезапуском
  (`autossh` или `ssh -N` + `Restart=always`).
- Контейнеру шлюза — `HTTPS_PROXY` на адрес туннеля, и `NO_PROXY` со всем, что должно
  идти напрямую: региональный провайдер, локальные модели, адресация LAN.
- Ключ ssh на зарубежном хосте ограничить так, чтобы им нельзя было ни получить shell,
  ни пробросить что-либо кроме этого порта: `command="/bin/false",restrict,`
  `port-forwarding,permitopen="127.0.0.1:<порт>"`.

Проверка шага: `curl -x <прокси> -o /dev/null -w '%{http_code}' https://openrouter.ai/api/v1/models`
изнутри хоста шлюза → 200. Без прокси — ожидаемо 403, и это нормально.

## Шаг 3. Маршруты и уровни данных

В конфиге шлюза завести короткие имена, за которыми стоят конкретные модели. Минимальный
набор, где каждое имя закрывает свою роль:

| Имя | Что за ним | Для чего |
|---|---|---|
| `fast` | дешёвая модель с большим контекстом | массовая разметка, классификация, суммаризация |
| `smart` | сильная reasoning-модель | сложный разбор, код, длинные цепочки с инструментами |
| `vision` | дешёвая модель, принимающая изображения | скриншоты, фото документов |
| `regional` | провайдер, которому можно отдавать приватное | всё, что нельзя за границу |
| `local` | модель на том же хосте (Ollama и подобное) | закрытый контур, классификация, офлайн |
| `local-embed` | эмбеддинги локально | векторный поиск |

Правила, которые надо записать комментарием в первой строке конфига и дальше соблюдать:

- Имена моделей у провайдера **пинятся по версии**. Плавающие указатели («latest»)
  существуют, но дрейфуют — поведение меняется без предупреждения.
- Для каждого имени задать fallback-цепочку: падение одного провайдера не должно
  останавливать ботов. Цепочка не должна выводить приватные данные за границу — у
  `regional` fallback только на `local`.
- `drop_params: true` (провайдеры по-разному реагируют на незнакомые параметры) и
  потолок `max_tokens` с запасом — см. грабли про reasoning.

Проверка шага: по каждому имени пройти смоук-запрос и увидеть осмысленный ответ. **Не
верить конфигу без запроса**: опечатка в имени модели у провайдера выясняется только
живым вызовом.

## Шаг 4. Изоляция контуров ключами

Главная идея: разделение держится не на коде ботов, а на ключах шлюза. Даже если бот
ошибётся и попросит запрещённую модель, шлюз откажет.

- Мастер-ключ **не отдавать ни одному боту**. Им создаются остальные ключи, он же даёт
  админ-API шлюза: создание ключей, чтение логов расхода.
- На каждого бота (или каждую роль) — свой virtual key с явным списком моделей,
  бюджетом и периодом. Ключ с приватным контуром не содержит облачных маршрутов, и
  наоборот.
- Если нужен общий потолок на всех ботов — завести команду (`/team/new`) с бюджетом и
  включить ключи в неё: лимит ключа и лимит команды работают вместе.
- Полезные поля ключа, которые работают в бесплатной версии: `models`, `max_budget` +
  `budget_duration`, `rpm_limit`/`tpm_limit`, `aliases` (ключ подменяет имя модели — так
  модель боту меняется без правки его конфига и перезапуска).

Проверка шага: ключом приватного контура позвать облачную модель → отказ; облачным
ключом позвать региональную → отказ. Обе проверки обязательны, достаточно одной
пропущенной, чтобы схема оказалась декоративной.

## Шаг 5. Telegram-бот с ролями

Бот — тонкий клиент: HTTP к шлюзу, никакой логики провайдеров внутри.

Структура роли (файл на роль, не ветки `if` в коде):

```
roles/
  assistant/SYSTEM.md    # системный промпт
  coach/SYSTEM.md
  analyst/SYSTEM.md
  roles.yaml             # роль → {модель по умолчанию, ключ шлюза, уровень данных}
```

Требования к боту:

- **Белый список user id.** Любое сообщение не из списка игнорируется молча. Без этого
  бот становится публичным прокси к платным моделям.
- `/role` — список ролей и переключение; выбранная роль живёт в состоянии чата.
- История диалога — на роль и на чат, с ограничением по длине; переключение роли
  историю не смешивает.
- `/new` — сброс контекста.
- Таймауты и дружелюбный текст ошибки: шлюз может отвечать минуту на reasoning-модели.
- Логировать `httpx`/`requests` на уровне WARNING. На INFO клиент печатает URL запроса,
  а в URL Telegram API входит токен бота — это утечка токена в журнал.

Если роль работает с приватными данными, а задача просит облачную модель — спросить
человека кнопками «отдать / остаться локально», и **отказ не должен отменять запрос**:
он выполняется на региональной модели. Решение помнить на сессию, не навсегда.

Классифицировать приватность стоит в два шага: стоп-лист по явным маркерам (документы,
финансы, адреса, переписка, рабочие пути) и локальная модель на остальном. Любая ошибка
классификации трактуется как «приватное»: лишний вопрос дешевле утечки. Классификацию
**никогда** не выносить в облако — чтобы узнать, можно ли отдавать текст наружу,
пришлось бы отдать его наружу.

Проверка шага: от каждой роли пройти по одному запросу, увидеть в `LiteLLM_SpendLogs`
записи с разными `user_api_key_alias` и ожидаемыми моделями.

## Шаг 6. Наблюдаемость

- Расход: `select coalesce(metadata->>'user_api_key_alias','(master)'), model, count(*), sum(spend) ... group by 1,2`.
- Health-проверка шлюза во внешнем мониторинге (Gatus, Uptime Kuma) — но алерт о
  поломке шлюза не должен идти через бота, который сам зависит от шлюза.
- Бэкап БД шлюза проверять восстановлением, а не наличием файла.

## Грабли (собраны на живой установке)

| Симптом | Причина | Что делать |
|---|---|---|
| `CONNECT` через прокси падает с 500 | `BindSame yes` в tinyproxy привязывает исходящее соединение к адресу входящего (loopback) | убрать опцию |
| ssh-ключ посредника даёт shell | `restrict` в `authorized_keys` **не** запрещает команды | добавить `command="/bin/false"` |
| SOCKS-прокси не работает из контейнера шлюза | в образе нет `socksio` | только HTTP-прокси |
| `400 ... is not a valid model ID` | у провайдера плавающие указатели живут под именем с префиксом (например, с тильдой), а точные версии — без | пинить версию, не указатель |
| Модель вернула пустой `content`, `finish_reason=length` | reasoning-модель израсходовала весь `max_tokens` на размышление | потолок с запасом; где есть `reasoning_effort` — управлять им |
| Фильтр `startTime > now() - interval` по логам расхода отдаёт пусто | время события пишется в UTC, `now()` отдаёт время в часовом поясе БД | сравнивать с поправкой на смещение |
| Бюджет на конкретную модель внутри ключа не создаётся (500 с требованием лицензии) | `model_max_budget` и `tags` — платные функции | ограничивать списком моделей, а не деньгами на модель |
| Эмбеддинги у регионального провайдера отдают 402 | не оплачены тарифом | векторизация локальной моделью |
| Деплой снёс `.env` на сервере | `rsync --delete`: секретов нет в git, значит для синхронизации они «лишние файлы» | в скрипте деплоя `--delete` не использовать вообще, `.env` исключать явно |
| После обновления ядра пропал сетевой модуль | DKMS собран без установленного метапакета заголовков | ставить метапакет headers, а не конкретную версию |

## Чего не делать

- Не отдавать мастер-ключ боту. Ни одному, ни «временно для теста».
- Не включать `latest` ни для образа шлюза, ни для имени модели.
- Не публиковать шлюз в интернет «на время настройки».
- Не хранить реальные ключи в репозитории, в том числе в приватном.
- Не править конфиг на сервере руками без бэкапа и записанной команды отката.
- Не считать схему рабочей, пока не выполнены обе проверки изоляции из шага 4.

## Порядок сдачи

1. Шлюз поднят, health и `/v1/models` отвечают.
2. Смоук по каждому имени модели — ответы приложить.
3. Обе проверки изоляции ключей — вывод приложить.
4. Бот отвечает от каждой роли, в логах расхода видны разные ключи.
5. README в репозитории владельца: адреса, имена моделей, где лежат секреты, процедура
   деплоя, процедура откату, и раздел «грабли» с тем, что всплыло на этой установке.
