# Инструкция: подключение TrueNAS SCALE к своему exit-VPS и маршрутизация приложений

Продолжение [инструкции по exit-VPS](vpn-exit-vps-setup-2026-10.md). Там поднимался сервер с
тремя транспортами — Reality, Hysteria2, AmneziaWG. Здесь — клиентская часть на **TrueNAS
SCALE** и, главное, корректная маршрутизация: как завернуть в туннель ровно те приложения,
которым это нужно, не потеряв веб-интерфейс NAS, доступ из локальной сети и возможность
обновлять саму систему.

Серверная часть (первый документ) проверена в проде с мая 2026. Этот документ — перенос той
же схемы на TrueNAS, платформу с особым устройством: специфика версий и механизмов сверена
по документации TrueNAS 25.04/25.10 в октябре 2026, схема sidecar-шлюза — стандартная и
широко обкатанная, но проверять её на своей установке **обязательно** по приёмке из
раздела 9. Она там подробная именно поэтому.

Адреса, порты, имена пулов и ключи — заглушки вида `<...>`.

## Что получится

| Цель | Как проверяется |
|---|---|
| Выбранные приложения выходят в интернет через ваш VPS | `curl` из контейнера приложения отдаёт IP VPS |
| Остальные приложения и сам NAS ходят напрямую | `curl` на хосте отдаёт домашний IP |
| Веб-интерфейсы завёрнутых приложений доступны из локальной сети | открывается по `http://<nas>:<port>` |
| Падение туннеля не даёт утечки реального IP | останов туннеля → у приложения нет сети вовсе, а не прямой выход |
| DNS-запросы завёрнутых приложений не утекают провайдеру | `dig` изнутри идёт через туннель |
| Схема переживает перезагрузку NAS | после ребута всё поднялось само |
| Схема переживает обновление TrueNAS | после апгрейда всё поднялось само |

## Чего здесь нет

Шлюз для всей домашней сети (это задача роутера, не NAS) и клиенты на телефонах/ноутбуках —
отдельные документы. Здесь только NAS и то, что на нём работает.

## 1. Главное про TrueNAS: это appliance, а не Debian

TrueNAS собран на Debian, и это вводит в заблуждение. Корневая файловая система защищена
от записи, `apt` по умолчанию отключён — именно чтобы случайная установка пакета не сделала
систему неработоспособной. Снять защиту можно (`install-dev-tools`), но:

- изменения **не выживают обновление системы** — команду придётся повторять после каждого
  апдейта;
- на такую систему **не распространяется поддержка** производителя;
- `/usr` в части конфигураций примонтирован через `systemd-sysext` и остаётся read-only даже
  после снятия защиты.

**Вывод, определяющий всю дальнейшую архитектуру: никакие бинарники VPN-клиента в хост-ОС
не ставятся.** Ни xray, ни hysteria, ни amneziawg. Всё живёт в контейнерах, конфиги — в
датасете на пуле данных.

Отдельное следствие для AmneziaWG: модуля ядра на TrueNAS нет, а собрать его через DKMS
нечем — нет заголовков ядра и нет права писать в `/usr`. Поэтому **только
userspace-реализация** `amneziawg-go` внутри контейнера с `NET_ADMIN` и `/dev/net/tun`.
В первом документе userspace выбран из-за мины с обновлениями ядра; здесь у него вообще нет
альтернативы.

### Где что хранить

| Что | Где | Переживёт апгрейд |
|---|---|---|
| Определения приложений (compose) | Apps → **Install via YAML** (хранится в конфиге TrueNAS) | да |
| Конфиги, ключи, скрипты | датасет на пуле данных: `/mnt/<pool>/apps/vpn-gw/` | да |
| Docker-образы | пул приложений | да |
| Пакеты, установленные через `apt` | хост-ОС | **нет** |
| Правки файлов вне `/mnt` | хост-ОС | **нет** |
| Init/Shutdown-скрипты из UI | конфиг TrueNAS (System → Advanced) | да (но не пережуют замену boot-пула) |

### Версии

| Версия | Имя | Что важно |
|---|---|---|
| 24.10 | Electric Eel | приложения переехали с Kubernetes на **Docker** — вся схема ниже требует минимум этой версии |
| 25.04 | Fangtooth | появились Containers/Instances (на Incus) и VM — модель C ниже |
| 25.10 | Goldeye | Incus убран, LXC переехал на libvirt; Custom App via YAML на месте |

На 24.04 и старше (k3s-эпоха) эта инструкция не применима: там другой механизм приложений.

### Как разворачивается своё приложение

Apps → Discover → меню «⋮» → **Install via YAML** → поле **Custom Config**, куда вставляется
docker-compose YAML. Имя приложения — строчные буквы и цифры, начинается с буквы, дефис
допустим не первым и не последним символом. Файл должен начинаться с элемента верхнего
уровня (`name:`, `services:` или `include:`).

Ключ `include:` позволяет держать свой compose-файл в датасете и ссылаться на него — удобно,
если вы правите YAML в редакторе, а не в браузере:

```yaml
include:
  - /mnt/<pool>/apps/vpn-gw/docker-compose.yml
```

Запускать `docker compose up` руками из shell не стоит: такие контейнеры не видны UI
и не управляются им. Пулом приложений должен быть выбран пул данных (Apps → Configuration),
иначе приложения просто не запустятся.

## 2. Выбор модели маршрутизации

Три рабочих варианта. Выбор не косметический — он определяет, что сломается при отказе.

| | A. Sidecar-шлюз в контейнере | B. Policy routing на хосте | C. Отдельный LXC/VM-шлюз |
|---|---|---|---|
| Суть | контейнер с туннелем, приложения делят с ним сетевое пространство | tun-интерфейс на хосте + правила маршрутизации по метке/адресу | гостевая система как маршрутизатор |
| Что идёт через VPN | ровно прицепленные контейнеры | то, что попало под правило | то, что указали шлюзом |
| Веб-UI NAS | не затрагивается вовсе | **под риском** | не затрагивается |
| Переживает апгрейд | да | хрупко: правила в init-скриптах, tun на хосте | да |
| Отладка | `docker exec`, всё в одном месте | тяжёлая: правила ядра на appliance | обычная Linux-отладка |
| Цена | порты публикуются на шлюзе, рестарты связаны | риск потерять доступ к NAS | ещё одна система для обслуживания |
| Когда брать | **по умолчанию** | почти никогда | NAS как шлюз для других устройств, либо хочется «весь NAS в туннель» |

**Рекомендация: A.** Она даёт ровно то, что обычно нужно («торрент-клиент и пара сервисов
наружу через зарубежный IP, остальное напрямую»), и физически не способна отрезать доступ к
NAS: маршруты хоста не трогаются ни одной командой.

**B не рекомендую** и описываю в разделе 7 только для полноты. На appliance это означает
правила маршрутизации в init-скриптах, которые выполняются до поднятия контейнера с туннелем,
и отладку в условиях, где любая ошибка в `ip rule` отрезает веб-интерфейс NAS вместе с SSH.

**C берите, если** нужно, чтобы через туннель ходили не приложения NAS, а другие устройства
сети, или если нужен именно «весь NAS целиком». Внутри гостя — первая инструкция, раздел
«клиентская часть», плюс форвардинг и NAT как в её разделе 5.3.

### Чего в туннель заворачивать не надо

Сам вопрос «а давайте весь NAS через VPN» обычно снимается этой таблицей:

| Сервис | Через VPN? | Почему |
|---|---|---|
| Торрент-клиент | да | ровно та задача, для которой это делается |
| Сервисы, которым нужен зарубежный IP (региональные API, индексаторы) | да | иначе не работают |
| Plex / Jellyfin / Emby | **нет** | ломается внешний доступ и прямое воспроизведение, скорость падает |
| Immich / Nextcloud / фотобэкап с телефона | **нет** | внешний доступ и мобильная синхронизация завязаны на прямой канал |
| SMB / NFS / iSCSI | **нет** | это локальный трафик, в туннеле ему делать нечего |
| Обновления TrueNAS, выгрузка бэкапов | **нет** | гигабайты в лимит трафика VPS |
| Мониторинг и алерты | **нет** | алерт о сломанном канале не должен идти по этому каналу |

Последний пункт — не вкусовщина, а арифметика: трафик VPS обычно ограничен 2–3 ТБ в месяц,
а NAS с медиатекой выедает это за неделю, после чего канал уходит в soft-cap и портится
связь у всех остальных клиентов.

## 3. Подготовка

### 3.1 Датасет под шлюз

Через UI (Datasets → Add Dataset) или в shell:

```sh
zfs create <pool>/apps/vpn-gw
mkdir -p /mnt/<pool>/apps/vpn-gw/{conf,build}
chmod 700 /mnt/<pool>/apps/vpn-gw/conf     # внутри лежат приватные ключи
```

### 3.2 Проверка tun

```sh
ls -l /dev/net/tun        # должен существовать
lsmod | grep -w tun       # либо модуль загружен, либо встроен в ядро
```

Если устройства нет — `modprobe tun`, и команду в System → Advanced → Init/Shutdown Scripts
как **Pre Init**, чтобы не отваливалось после ребута.

### 3.3 Клиентские параметры с сервера

С exit-VPS понадобятся (см. первый документ):

| Для чего | Что |
|---|---|
| AmneziaWG | публичный ключ сервера, PSK пира, адрес пира из подсети туннеля, порт, все параметры обфускации (`Jc/Jmin/Jmax/S1/S2/H1..H4`) **байт в байт** |
| Reality | UUID, публичный ключ, shortId, SNI/домен маскировки, порт |
| Hysteria2 | пароль auth, пароль obfs, домен маскировки, порт |

Приватный ключ клиента генерируется здесь, на NAS, и на сервер уезжает только публичный.

## 4. Модель A: шлюз в контейнере

Транспорт основной — **AmneziaWG**, потому что он даёт настоящий L3-интерфейс: маршрут по
умолчанию, простой аварийный блокиратор, работает для любого приложения, ничего не зная о
нём. Reality и Hysteria2 — это SOCKS/HTTP-прокси; чтобы завернуть в них весь трафик сетевого
пространства, нужен дополнительный слой (tun2socks или прозрачный перехват), и как **основной**
путь это лишняя деталь. Их роль здесь — резерв, если UDP-порт AmneziaWG зарежут, и прямое
подключение для приложений, которые сами умеют SOCKS5 (торрент-клиенты умеют).

### 4.1 Образ

Готового официального образа `amneziawg-go` нет. Через этот бинарь пойдёт весь трафик, так
что лучше собрать свой из исходников, как в первом документе — и запинить теги.

`/mnt/<pool>/apps/vpn-gw/build/Dockerfile`:

```dockerfile
FROM golang:1.22-bookworm AS build
RUN apt-get update && apt-get install -y --no-install-recommends git make build-essential \
 && rm -rf /var/lib/apt/lists/*
WORKDIR /src
ARG AWG_GO_REF=<TAG_OR_COMMIT>
ARG AWG_TOOLS_REF=<TAG_OR_COMMIT>
RUN git clone https://github.com/amnezia-vpn/amneziawg-go.git \
 && cd amneziawg-go && git checkout ${AWG_GO_REF} && make
RUN git clone https://github.com/amnezia-vpn/amneziawg-tools.git \
 && cd amneziawg-tools && git checkout ${AWG_TOOLS_REF} \
 && cd src && make && make install DESTDIR=/out

FROM debian:bookworm-slim
RUN apt-get update && apt-get install -y --no-install-recommends \
      iproute2 iptables iputils-ping procps curl ca-certificates dnsutils \
 && rm -rf /var/lib/apt/lists/*
COPY --from=build /src/amneziawg-go/amneziawg-go /usr/local/bin/amneziawg-go
COPY --from=build /out/usr/bin/ /usr/bin/
COPY entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh
ENTRYPOINT ["/entrypoint.sh"]
```

Пути внутри репозиториев у разных тегов немного отличаются — после сборки проверьте, что
`awg` и `awg-quick` действительно оказались в `/usr/bin`:

```sh
cd /mnt/<pool>/apps/vpn-gw/build
docker build -t awg-gw:<TAG> .
docker run --rm awg-gw:<TAG> sh -c 'awg --version; which awg-quick amneziawg-go'
```

### 4.2 Конфиг туннеля

`/mnt/<pool>/apps/vpn-gw/conf/awg0.conf` (режим `600`):

```ini
[Interface]
PrivateKey = <CLIENT_PRIVATE_KEY>
Address = 10.<X>.<Y>.<N>/32
# 1280 — безопасный потолок. Обфускация добавляет свои байты к каждому пакету,
# и при MTU 1420 крупные ответы начинают зависать на середине.
MTU = 1280
# DNS здесь НЕ указывать: awg-quick попытается вызвать resolvconf, которого
# в slim-образе нет, и упадёт. DNS задаётся в compose (раздел 4.4).

# Параметры обфускации — ровно те же, что на сервере. Расхождение в одном
# числе = рукопожатие не состоится, и внятной ошибки не будет.
Jc = 4
Jmin = 40
Jmax = 70
S1 = 50
S2 = 100
H1 = <RANDOM_1>
H2 = <RANDOM_2>
H3 = <RANDOM_3>
H4 = <RANDOM_4>

[Peer]
PublicKey = <SERVER_PUBLIC_KEY>
PresharedKey = <PEER_PSK>
Endpoint = <VPS_IP>:<AWG_PORT>
AllowedIPs = 0.0.0.0/0
PersistentKeepalive = 25
```

`AllowedIPs = 0.0.0.0/0` означает «весь трафик в туннель». `awg-quick` реализует это не
подменой маршрута по умолчанию, а правилами с метками, что автоматически выводит из туннеля
сами пакеты туннеля — отдельного исключения для адреса VPS делать не нужно.

### 4.3 entrypoint: туннель, обратный маршрут в сеть, аварийный блокиратор

`/mnt/<pool>/apps/vpn-gw/build/entrypoint.sh`. Три вещи, которые делает скрипт, и каждая
из них — ответ на конкретную поломку:

```sh
#!/bin/sh
set -eu

: "${LAN_SUBNET:?LAN_SUBNET не задан}"     # например 192.168.<x>.0/24
: "${VPS_IP:?VPS_IP не задан}"
: "${AWG_PORT:?AWG_PORT не задан}"

# Шлюз бриджа и своя подсеть — ЗАПОМНИТЬ ДО подъёма туннеля: после него
# маршрут по умолчанию уже другой.
BRIDGE_GW=$(ip route show default | awk '{print $3; exit}')
BRIDGE_NET=$(ip -o -4 addr show dev eth0 | awk '{print $4}')

[ -c /dev/net/tun ] || { echo "нет /dev/net/tun — проверьте devices и cap_add"; exit 1; }

# Конфиг смонтирован только для чтения — awg-quick правит его на лету,
# поэтому работаем с копией в ожидаемом им каталоге.
mkdir -p /etc/amnezia/amneziawg
cp /conf/awg0.conf /etc/amnezia/amneziawg/awg0.conf
chmod 600 /etc/amnezia/amneziawg/awg0.conf

awg-quick up awg0
awg show awg0

# (1) Обратный маршрут в локальную сеть.
# Без него веб-интерфейсы прицепленных приложений недоступны из LAN: запрос
# приходит через бридж, а ответ уходит в туннель и там теряется.
ip route add "$LAN_SUBNET" via "$BRIDGE_GW" dev eth0 2>/dev/null || true

# (2) Аварийный блокиратор. Если туннель упал или контейнер поднялся без него,
# трафик приложений должен НЕ ИДТИ, а не уходить напрямую.
iptables -F OUTPUT; iptables -F INPUT
iptables -P OUTPUT DROP
iptables -P INPUT  DROP
iptables -A OUTPUT -o lo -j ACCEPT
iptables -A INPUT  -i lo -j ACCEPT
iptables -A OUTPUT -o awg0 -j ACCEPT
iptables -A OUTPUT -d "$VPS_IP"/32 -p udp --dport "$AWG_PORT" -j ACCEPT
# локальный обмен: опубликованные порты и ответы в сеть
iptables -A OUTPUT -d "$BRIDGE_NET" -j ACCEPT
iptables -A OUTPUT -d "$LAN_SUBNET" -j ACCEPT
iptables -A INPUT  -s "$BRIDGE_NET" -j ACCEPT
iptables -A INPUT  -s "$LAN_SUBNET" -j ACCEPT
iptables -A INPUT  -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT

# (3) Корректное завершение, чтобы интерфейс не оставался при остановке.
trap 'awg-quick down awg0 || true; exit 0' TERM INT
echo "шлюз готов: $(ip route show default)"
while :; do sleep 3600 & wait $!; done
```

### 4.4 compose

```yaml
name: vpn-gw

services:
  vpn-gw:
    image: awg-gw:<TAG>
    container_name: vpn-gw
    restart: unless-stopped
    cap_add:
      - NET_ADMIN
    devices:
      - /dev/net/tun:/dev/net/tun
    sysctls:
      - net.ipv4.conf.all.src_valid_mark=1
    environment:
      LAN_SUBNET: <LAN_SUBNET>      # 192.168.<x>.0/24
      VPS_IP: <VPS_IP>
      AWG_PORT: <AWG_PORT>
    # DNS внутри сетевого пространства. Запрос уйдёт через туннель —
    # провайдер не увидит, что именно резолвится.
    dns:
      - 1.1.1.1
      - 9.9.9.9
    volumes:
      - /mnt/<pool>/apps/vpn-gw/conf:/conf:ro
    # Порты ВСЕХ прицепленных приложений публикуются здесь: у них нет
    # своего сетевого пространства, значит и своих портов тоже.
    ports:
      - "<APP_PORT>:<APP_PORT>"
    healthcheck:
      # Проверяем не интерфейс, а проход трафика: интерфейс может быть поднят
      # при мёртвом канале.
      test: ["CMD-SHELL", "curl -fsS --max-time 10 https://api.ipify.org >/dev/null"]
      interval: 60s
      timeout: 15s
      retries: 3
      start_period: 30s

  app:
    image: <APP_IMAGE>@sha256:<DIGEST>
    container_name: <app>
    restart: unless-stopped
    # Вот этой строкой приложение попадает в туннель. Своих ports/dns
    # у него теперь быть не может — они задаются на vpn-gw.
    network_mode: "service:vpn-gw"
    depends_on:
      vpn-gw:
        condition: service_healthy
    volumes:
      - /mnt/<pool>/apps/<app>/config:/config
      - /mnt/<pool>/<data_dataset>:/data
    healthcheck:
      test: ["CMD-SHELL", "curl -fsS --max-time 10 https://api.ipify.org >/dev/null"]
      interval: 60s
      timeout: 15s
      retries: 3

  # Рестарт vpn-gw рвёт сеть прицепленным контейнерам НАВСЕГДА — они остаются
  # привязанными к исчезнувшему сетевому пространству и сами не чинятся.
  # Этот контейнер перезапускает всё, что ушло в unhealthy.
  autoheal:
    image: willfarrell/autoheal@sha256:<DIGEST>
    container_name: vpn-gw-autoheal
    restart: unless-stopped
    environment:
      AUTOHEAL_CONTAINER_LABEL: all
      AUTOHEAL_INTERVAL: 30
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
```

Про `autoheal`: смонтированный `docker.sock` — это полный доступ к хосту для контейнера.
Для домашнего NAS компромисс обычно приемлем, но если нет — уберите сервис и перезапускайте
приложения вручную после каждого рестарта шлюза. Автоматически они не восстановятся.

### 4.5 Разворачивание

Apps → Discover → ⋮ → Install via YAML, имя `vpn-gw`, содержимое — YAML выше (или `include:`
на файл в датасете). После запуска:

```sh
docker exec vpn-gw awg show awg0
docker exec vpn-gw ip route show
docker exec <app> curl -s https://api.ipify.org    # IP вашего VPS
curl -s https://api.ipify.org                      # на хосте — домашний IP
```

### 4.6 Резервный транспорт

Если UDP до VPS зарежут (бывает выборочно: по автономной системе, по маршруту, по оператору),
AmneziaWG встанет, а Reality/Hysteria2 на том же сервере продолжат работать. Отдельный
контейнер с клиентом xray или sing-box, отдающий SOCKS5 в локальную сеть, закрывает два
случая:

- приложение умеет SOCKS5 само (торрент-клиенты умеют) — прописать прокси в его настройках
  и не зависеть от шлюза вовсе;
- шлюз из 4.4 можно переключить на этот прокси через tun2socks, если AmneziaWG недоступен
  долго.

Такой контейнер работает в обычном bridge-режиме, порт SOCKS публикуется на хост, через
туннель его трафик **не** идёт — он сам и есть канал. Конфиги клиента — из первого документа
(те же UUID/SNI/пароли, что на сервере).

## 5. Если нужно завернуть уже установленное приложение из каталога

Приложения из каталога TrueNAS (Apps → Discover) ставятся своим механизмом, и поля
`network_mode` у них в UI нет. Варианты:

1. **Переустановить приложение как Custom App** в том же compose, что и шлюз — данные
   остаются, если смонтировать те же датасеты. Предпочтительный путь: всё описано в одном
   месте, зависимости и healthcheck работают штатно.
2. **Оставить каталожное приложение и настроить в нём SOCKS5-прокси** (раздел 4.6), если оно
   это умеет. Быстро, но защиты от утечки при падении прокси нет — приложение просто пойдёт
   напрямую, и это надо проверять отдельно.

Смешивать не стоит: приложение либо в сетевом пространстве шлюза, либо нет.

## 6. Модель C: отдельный LXC-контейнер или виртуальная машина

Когда нужен не «несколько приложений наружу», а полноценный шлюз — например, чтобы через
туннель ходили другие устройства сети, или чтобы NAS целиком выходил зарубежным адресом.

- В 25.04 это **Instances/Containers** (на Incus) и Virtual Machines.
- В 25.10 Incus убран, LXC работает через libvirt. Если планируете апгрейд — учитывайте, что
  гость придётся переносить; виртуальная машина в этом смысле спокойнее контейнера.

Внутри гостя — обычный Debian, то есть применима первая инструкция без оговорок: клиент
AmneziaWG (или xray/hysteria), затем форвардинг и NAT из её раздела 5.3, только наоборот —
NAT не в интернет, а в туннель:

```sh
sysctl -w net.ipv4.ip_forward=1
iptables -t nat -A POSTROUTING -o awg0 -j MASQUERADE
iptables -A FORWARD -i <lan_iface> -o awg0 -j ACCEPT
iptables -A FORWARD -i awg0 -o <lan_iface> -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
```

Дальше устройства, которым нужен туннель, получают этот гость шлюзом по умолчанию — через
DHCP-резервацию на роутере или вручную. Гостю нужен адрес в локальной сети напрямую: для
виртуальной машины это bridge-интерфейс, не NAT.

Аварийный блокиратор здесь — то же, что в 4.3, но в цепочке FORWARD: при падении `awg0`
форвардинг должен прекратиться, а не уйти в обычный канал.

## 7. Модель B: маршрутизация на хосте — почему не стоит

Для полноты: технически это делается через tun-интерфейс, поднятый контейнером в сетевом
пространстве хоста (`network_mode: host`), и правила вида «трафик от такого-то адреса или с
такой-то меткой — в таблицу с маршрутом в туннель», положенные в Post Init script.

Почему я этого не рекомендую:

- **Порядок запуска не в вашу пользу.** Init-скрипты выполняются до старта приложений, то
  есть до поднятия туннеля: правило ссылается на интерфейс, которого ещё нет.
- **Ошибка стоит доступа к NAS.** Неверный `ip rule` на appliance отрезает веб-интерфейс и
  SSH одновременно, а отката «по таймеру» в TrueNAS нет — придётся идти к монитору и
  клавиатуре.
- **Апгрейд системы не обязан это пережить.** Скрипт в конфиге сохранится, а вот поведение
  сети вокруг него может измениться между версиями — и выяснится это после перезагрузки.
- **Отладка хуже.** В модели A всё состояние внутри одного контейнера: `docker exec`,
  `ip route`, `iptables -L` — и ничего не сломано снаружи.

Если всё-таки идёте этим путём: заранее подготовьте физический доступ к машине, держите
второй скрипт, возвращающий маршруты в исходное состояние, и не трогайте маршрут по
умолчанию хоста — только дополнительные таблицы для выбранных источников.

## 8. Эксплуатация

### Обновление TrueNAS

Определения приложений и датасеты апгрейд переживают, но проверять надо каждый раз:

```sh
docker ps --format '{{.Names}}\t{{.Status}}'       # все ли поднялись и healthy
docker exec vpn-gw awg show awg0                   # есть ли свежее рукопожатие
docker exec <app> curl -s https://api.ipify.org    # идёт ли трафик через туннель
ls -l /dev/net/tun                                 # устройство на месте
```

Если `/dev/net/tun` исчез — вернуть `modprobe tun` в Pre Init script (раздел 3.2).

### Бэкап

Выгружать и хранить:

- **конфигурацию TrueNAS** (System → General → Manage Configuration → Download File) — в ней
  живут определения приложений и init-скрипты;
- датасет `/mnt/<pool>/apps/vpn-gw/` — там ключи и Dockerfile; **приватные ключи в открытом
  виде**, так что либо приватный репозиторий, либо шифрование;
- параметры подключения к серверу — в парольном менеджере, а не только на NAS: при его
  потере восстанавливать придётся с чистого листа.

### Мониторинг

Проверять именно проход трафика (внешний адрес и доступность), а не состояние интерфейса:
туннель может быть поднят при мёртвом канале, что и ловит healthcheck из 4.4. Алерты не
должны ходить через проверяемый канал.

## 9. Приёмка

Пройти целиком — это и есть замена фразы «проверено у меня».

```sh
# 1. Шлюз жив и трафик идёт через VPS
docker exec vpn-gw awg show awg0 | grep -E 'latest handshake|transfer'
docker exec vpn-gw curl -s https://api.ipify.org          # ждём IP VPS

# 2. Приложение в туннеле, хост — нет
docker exec <app> curl -s https://api.ipify.org           # IP VPS
curl -s https://api.ipify.org                             # домашний IP

# 3. DNS не утекает: запрос должен уходить через туннель
docker exec vpn-gw dig +short myip.opendns.com @resolver1.opendns.com   # IP VPS
```

| Проверка | Как | Ожидание |
|---|---|---|
| Веб-UI завёрнутого приложения из LAN | открыть `http://<nas_ip>:<APP_PORT>` с другого устройства | открывается |
| Аварийный блокиратор | `docker exec vpn-gw awg-quick down awg0`, затем `docker exec <app> curl -m 10 https://api.ipify.org` | ошибка/таймаут, **не** домашний IP |
| Восстановление | `docker restart vpn-gw`, подождать healthcheck | приложения снова в туннеле (autoheal перезапустит) |
| Веб-интерфейс NAS | открыть с другого устройства | доступен (модель A его не трогает в принципе) |
| MTU | скачать через завёрнутое приложение файл ≥50 МБ | без зависаний на середине |
| Ребут NAS | перезагрузить | всё поднялось само, туннель активен |
| Апгрейд TrueNAS | после обновления — блок команд выше | всё поднялось само |
| Незавёрнутые сервисы | проверить внешний доступ к Plex/Immich | работают как раньше |

## 10. Грабли

| Симптом | Причина | Что делать |
|---|---|---|
| Веб-UI завёрнутого приложения не открывается из сети | ответ уходит в туннель вместо бриджа | обратный маршрут на LAN-подсеть внутри шлюза (4.3, пункт 1) |
| Порт приложения «не публикуется» | порты объявлены у приложения, а своего сетевого пространства у него нет | переносить `ports` на контейнер шлюза |
| После рестарта шлюза приложения без сети навсегда | docker не переподключает контейнер к исчезнувшему netns | healthcheck + autoheal (4.4) либо ручной рестарт |
| Рукопожатие есть, трафика нет | расходятся параметры обфускации, либо MTU, либо на сервере нет форвардинга/NAT | сверить `Jc/Jmin/Jmax/S1/S2/H1..H4` с сервером; MTU 1280; раздел 5.3 первой инструкции |
| Контейнер падает при старте с ошибкой resolvconf | `DNS =` в конфиге туннеля, а resolvconf в образе нет | убрать `DNS =`, задать `dns:` в compose |
| `operation not permitted` при подъёме интерфейса | нет `NET_ADMIN` или `/dev/net/tun` | `cap_add` + `devices` в compose |
| Крупные файлы качаются до середины и встают | MTU | 1280 на интерфейсе туннеля |
| Провайдер видит, какие домены резолвятся | DNS мимо туннеля | `dns:` на шлюзе, проверка через `dig` (раздел 9) |
| При падении туннеля приложение продолжает качать | нет аварийного блокиратора | правила из 4.3, пункт 2, и обязательно проверить их по разделу 9 |
| После обновления TrueNAS пропали бинарники/пакеты | их ставили в хост-ОС | переносить в контейнер (раздел 1) |
| Трафик VPS исчерпан за неделю | в туннель завёрнуто лишнее | таблица в разделе 2 |
| Приложения вообще не стартуют | не выбран пул приложений | Apps → Configuration |
